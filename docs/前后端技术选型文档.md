# MovieRecommender 前后端技术选型文档

## 1. 文档目标与范围

本文档基于当前 `MovieRecommender-later` 项目现状，给出可落地的前后端技术选型说明，覆盖：

- 已采用技术与版本
- 选型原因与业务匹配度
- 可替代方案对比
- 当前风险与演进建议

> 适用对象：项目负责人、架构师、后端/前端开发、运维与测试。

---

## 2. 项目现状概览（与现有代码一致）

### 2.1 后端现状

后端以 **Java 8 + Spring Boot 2.7.18** 为核心，采用 **MyBatis + MySQL** 完成数据访问，使用 **Apache Mahout** 提供推荐算法能力，并结合 **Caffeine** 缓存提升推荐与查询性能，同时集成 **TMDb API** 补全电影海报等元数据。

### 2.2 前端现状

前端基于 **Vue 3 + Vite + PrimeVue** 构建，使用 **Vue Router** 路由、**Pinia** 状态管理、**Axios** 统一请求层，形成前后端分离的 SPA 应用。

## 4. 选型理由（结合本项目业务）

### 4.1 后端为什么是 Spring Boot + MyBatis + Mahout

1. **推荐业务可快速落地**
   - Mahout 已提供协同过滤相关实现，能较快支撑“用户协同过滤 / 物品协同过滤 / Slope One”三类能力。
2. **数据访问可精细化优化**
   - 推荐场景中常见批量查询、统计查询、流式加载，MyBatis 在 SQL 可控性方面更有优势。
3. **接口服务化能力成熟**
   - Spring Boot 适合快速构建 REST API，且方便接入监控、缓存、异步任务。
4. **性能与稳定性平衡**
   - 通过 Caffeine 本地缓存 + 数据模型预热 + 定时重建，适配中小规模推荐服务的性能需求。

### 4.2 前端为什么是 Vue 3 + Vite + PrimeVue

1. **页面类型匹配**
   - 本项目以前台展示 + 数据列表 + 交互表单为主，PrimeVue 组件可覆盖大多数场景。
2. **迭代效率高**
   - Vite 开发体验优于传统构建工具，适合快速迭代推荐策略展示页。
3. **工程结构清晰**
   - API 层、路由、状态、页面拆分明确，便于多人协作。
4. **前后端分离契合度高**
   - Axios + OpenAPI 文档可显著降低接口对接成本。

## 5. 可替代方案与对比

### 5.1 后端可替代方案

| 方案 | 优点 | 缺点 | 适用时机 |

## 6. 当前选型风险与治理建议

### 6.1 风险点

1. **Java 8 与 Spring Boot 2.7 的长期维护风险**：后续安全更新与生态升级空间受限。
2. **Caffeine 为本地缓存**：多实例部署时缓存不一致。
3. **推荐模型主要基于协同过滤**：冷启动与长尾内容推荐能力有限。
4. **外部 TMDb API 依赖**：存在限流、网络波动对体验的影响。

### 6.2 治理建议

1. **后端升级路线**：分阶段升级到 Java 17 + Spring Boot 3.x。
2. **缓存架构升级**：单机阶段继续使用 Caffeine；多副本阶段引入 Redis 二级缓存。
3. **推荐能力增强**：在协同过滤基础上叠加内容特征召回与热门兜底策略。
4. **外部 API 稳定性**：增加重试、熔断、降级占位图与异步补偿任务。
5. **接口契约治理**：以 OpenAPI 作为前后端契约源，纳入 CI 校验。

---

## 7. 结论（建议保留当前主选型）

从项目目标（快速构建可用的电影推荐系统）与现有实现成熟度看，当前 **Vue 3 + Vite + PrimeVue（前端）** 与 **Spring Boot + MyBatis + Mahout（后端）** 的组合是“成本、速度、可维护性”之间较均衡的方案。

短期建议保持现有技术栈并补齐工程治理；中长期再推进 Java/Spring 升级与分布式缓存演进。
